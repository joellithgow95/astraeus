## What this repo is

**Astraeus** is a governed data platform for Python/Starlette developers. Eight packages:

- **`starlette-cms`** — headless CMS (block registry, document API, webhooks, schema versioning)
- **`starlette-editor`** — visual editing UI (ProseMirror-based, auto-generated from block schema)
- **`mediakit`** — media management (S3-compatible storage, IIIF Image API, presigned uploads)
- **`starlette-cms-gateways`** — framework for pulling external service data into the CMS as documents
- **`starlette-cms-feedback`** — feedback and bug reports: admin page, auth-gated HTTP API on the CMS, MCP tools
- **`starlette-chat`** — governed AI chat collaborator with live ProseMirror collab
- **`astraeus-otel`** — shared OpenTelemetry configuration and testing utilities
- **`astraeus-portal`** — central navigation hub linking all admin interfaces

Each package is built to be independently installable. **None are published to PyPI yet** — there are no release tags and the `version` fields are hand-set and stale, so a consumer depends on this workspace by path (see `joellithgow/pyproject.toml`). Versioning becomes worth setting up when the first package is actually published.

**Reading the rest of this file with that in mind:** "publish independently" below means *can be*, not *are*. `uv.lock` is generated by `uv sync` in each checkout and is gitignored; the workspace is one resolve, but that resolve is not committed.

**Why it exists:** Joel needed an agentic content backend for his personal site (joellithgow.com) and future client work. He wanted something he could use across projects — not a one-off backend. The agentic layer (MCP servers) is a first-class design goal, not a bolt-on.

**What it turned out to be:** Through real-world use, Astraeus has proven useful well beyond editorial content. Any structured data artifact that needs version history, authorship, approval workflow, and audit trail is a natural fit — intake forms, actuarial rule tables, AI pipeline prompts, eval datasets, curated test cases. The same primitives (blocks, documents, singletons, references, webhooks) serve all of these. See `docs/use-cases/` for worked examples.

## Conventions

### Code style
- Python 3.12+, type annotations everywhere
- Pydantic v2 for all data models
- `from __future__ import annotations` at the top of every file
- Async-first — all I/O is async
- Match the docstring style already in the codebase (brief summary, `::` code examples)

### Package boundaries
- `starlette-editor` depends on `starlette-cms` — never the reverse
- `mediakit` has no dependency on either CMS package
- `starlette-cms` has an optional soft dependency on `mediakit` via the `MediaBackend` protocol — it never imports mediakit directly

### Writing documents: the authority and the CRUD path (ADR 027)
A document is written two ways: the **collab path** (steps over the editor's WebSocket, applied in order by the field's `CollabAuthority`) and the **CRUD path** (`PATCH /api/documents/{id}`, which MCP `update_document`, scripts and gateways use). Which one a change takes depends on the field:
- **Rich-text fields (post bodies) have one writer: the authority.** To add to one, call `POST /api/documents/{id}/insert` (MCP `insert_into_document`) with markdown; it goes in as a step against the live document, so an open editor shows it and keeps its user's typing. Never rewrite a whole body to add to it.
- A whole rich-text replace through PATCH must carry `base_version` (the `draft_version` read with `?draft=true`); a stale one is refused with 409, and one is required while an editor has the field open.
- Plain fields (title, tags, image, dates, refs) stay CRUD. Lifecycle actions (publish, discard, changesets) stay commands, and any that changes a rich-text field must tell the authority (`CollabManager.apply_external_update`).
- New code that writes rich text from outside the editor goes through `CollabManager` (`insert_content`, `apply_external_update`), never straight to `draft_body`.

### Testing
- Every public function gets a test
- **Anything that touches draft, publish, changeset or sync-state semantics is tested against a real in-process CMS** (below), never against mocked HTTP: a mock can only say what you told it the CMS does. `respx` is for faking *external* services (iNaturalist, Spotify) and for pinning the request shape of pure client plumbing
- Use `starlette_cms.testing.RegistryTestCase` for tests that need a CMS instance — never share state between tests
- `httpx.AsyncClient` with `transport=ASGITransport(app=cms.app)` for HTTP endpoint tests

### Commits
- Conventional commits: `feat:`, `fix:`, `test:`, `docs:`, `chore:`
- End commit messages with a `Co-Authored-By:` line naming the model that wrote them

## Key decisions already made (don't relitigate)

- UV workspace monorepo — one workspace resolve (`uv.lock` is generated locally, gitignored, not committed); packages are built to publish independently, though none is published yet
- starlette-cms is headless-first — no built-in admin UI
- Plugin composition via `register_extension_route()` — editor extends CMS, not peer coupling
- MCP servers are optional HTTP client wrappers (`[mcp]` extra), not embedded in package core
- Webhooks handle build triggers — no direct Netlify/Vercel integration
- Content-addressed storage keys in mediakit (`originals/{sha256_prefix}/{filename}`)
- Two-form block decorator: `@cms.block()` (immediate) vs `@block()` (deferred/standalone)
- Rich text has one writer, the collab authority; plain fields stay CRUD (ADR 027, proposed)

See `docs/decisions/` for the full rationale on each.

**ADRs are immutable once written.** A decision that changes gets a *new* ADR that names what it supersedes; the old one only gains a status line pointing at it (ADR 015 → ADR 023 is the first case). Never amend an accepted ADR's decision in place. ADR 015's "Design History" amendments 1–4 predate this rule and stay as written.
